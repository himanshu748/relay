# Relay landing page thesis

Product truth: Incident response improves when a new agent session inherits the failures, constraints and hypotheses that already changed the last decision.

Audience: Hackathon judges, SREs and platform leaders who understand incident response but may doubt that agent memory is load bearing.

Desired feeling: Calm operational confidence. Precise, auditable and ready for a real incident.

Primary action: Run the memory test, which moves the visitor to the working incident console and starts a genuinely fresh agent session.

Visual concept: A black incident ledger with open editorial pacing. Thin evidence rails and numbered decision traces make the memory chain tangible without turning the page into a wall of cards.

Primary archetype: Technical instrument.

Secondary influence: Editorial narrative.

Page silhouette: Floating island navigation, asymmetric hero with a large working product frame, open proof bands, a full width tagline reveal, three numbered process rows, an official incident ledger with a deploy-survival receipt, focused FAQ and a final live demo invitation.

Type strategy: Geist throughout, with Geist Mono reserved for incident identifiers, API calls and numeric evidence. Hero uses the supplied white to gray text gradient. All sizes resolve to the supplied Tailwind scale.

Material and color language: True black canvas, flat #181818 and #1F1F1F surfaces, #313131 borders, bone white text, Sibyl green for recalled memory and Relay blue for actions. No background gradients.

Media strategy: The real Relay incident console is the primary visual. No fabricated logos, testimonials or stock media.

Signature moment: In the live console, a fresh session generates a visible recall receipt and changes the next action. The mid page tagline reveals word by word as the reader reaches the core proof.

Three cliches to avoid: Floating dashboard cards over a glow, a generic three column feature grid and fabricated customer logo strips.

## Hero copy

Headline: The next responder already knows what failed.

Subheadline: Relay gives incident response agents operational memory. A fresh session recalls failed remediation, operator constraints and live hypotheses before it recommends the next action.

Primary CTA: Run the memory test

Proof line: Built on Sibyl Memory, with a direct jump to the real GitHub Actions validation.

## Benefits

- Stop repeated remediation. Failed actions become blocked options in the next session.
- Preserve operator constraints. Safety rules survive handoffs and cold starts.
- Make recall auditable. Every decision shows the exact entity, state or event it used.

## How it works

1. Persist the incident. Relay writes observations, actions, constraints and hypotheses to Sibyl.
2. Start fresh. A new session loads the durable incident, HOT state and COLD journal.
3. Change the action. Recalled evidence blocks failed or unsafe steps and recomputes the recommendation.

## FAQ

1. Is this only a chat history wrapper? No. Relay reads persisted incident state before choosing an action and materially changes the recommendation.
2. What happens without Sibyl Memory? The fresh responder loses the failed restart and database constraint, then falls back to the repeated restart.
3. Is the fresh session real? Yes. Relay creates a new session identifier, reloads four memories and writes the receipt to the journal.
4. Can a responder add new evidence? Yes. Observations, actions, constraints and hypotheses are persisted during the incident.
5. Which memory primitives are used? Relay uses durable entities, HOT state and COLD events through the real Sibyl Memory client.
6. Is the recommendation generated by an external model? No. The current prototype uses deterministic logic so judges can reproduce the causal effect of memory without a model key.
